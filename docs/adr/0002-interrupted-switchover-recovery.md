# Сохранять обязанность завершить начатое переключение

После перезапуска manager локальная фаза теряется, а RunCount может оставаться нулевым даже после превращения старого мастера в реплику. Для switchover и failover сохраняем в DCS признак «изменения топологии уже могли начаться» после предварительных проверок и оптимизации, перед freeze. Без успешной записи признака freeze не начинается. После записи переключение нельзя отменять по таймауту или лимиту попыток, включая после смены manager; проверки кворума и сохранности данных продолжают действовать.

Принимаем консервативное восстановление, если процесс упал между записью признака и первым изменением MySQL. StartedAt остаётся временем начала попытки: он записывается до предварительных проверок и не доказывает начало изменений топологии.

Обновление должно поддерживать восстановление незавершённых операций старой версии без нового признака. Отсутствие поля само по себе не доказывает, что изменения ещё не начались. Для старых записей ненулевой StartedAt трактуем консервативно как возможное начало изменений даже при RunCount=0. Принимаем, что прерванная оптимизация старой версии тоже может потерять возможность отмены по таймауту. Новые записи должны отличать отсутствие признака от явного «изменения ещё не начались».

Выбранного нового мастера сохраняем перед началом перенаправления реплик. После этой границы цель сохраняется при смене manager; до неё допустим перевыбор с сохранением проверок данных.

После начала переключения по новому протоколу старые manager не должны получать управление до его завершения: перезапись запроса старой версией может удалить незнакомые поля. Поддержку свободного чередования старых и новых manager не проектируем.

Если новый мастер уже записан в DCS последним шагом переключения, а текущий запрос ещё существует, восстанавливаем оформление результата без повторного freeze. Сохранённая цель должна совпадать с мастером в DCS; противоречивое состояние не объявляем успешным автоматически.

Старые операции с известной целью восстанавливаем автоматически. Если у старой потенциально начатой операции нет To и сохранённой цели и прежнюю цель нельзя достоверно установить, оставляем запрос незавершённым с понятной диагностикой для оператора. Угадывание цели по графу репликации не реализуем.

## Минимальная реализация

Расширяем существующую запись Switchover двумя полями: TopologyStarted (*bool: отсутствие означает старый формат) и RecoveryTarget (имя зафиксированного нового мастера). Исходное To сохраняет смысл пользовательского запроса. Для новой операции явно записываем false до начала попытки; старую начатую запись нельзя при обновлении ошибочно превратить в новую неначатую.

Перед freeze сохраняем TopologyStarted=true, а после успешного catch-up, перед перенаправлением реплик, сохраняем RecoveryTarget. Ошибка записи останавливает дальнейшие изменения; обновление только локального объекта не считается успешным сохранением и не должно позволять следующей попытке пропустить запись.

Один общий предикат начала изменений используется при выборе мастера, проверке лимитов, запрете отмены и восстановлении локальной фазы. Для старого формата сохраняем консервативность RunCount>0 и добавляем StartedAt. Для нового формата источником истины служит сохранённый признак. При утрате локальной фазы используем существующий путь восстановления с учётом зафиксированной цели и отдельной проверки уже завершённого переключения.

Сохраняем существующие локальные фазы и механизм выполнения. Журнал всех фаз, новый исполнитель операций и новые зависимости для этого исправления не нужны. Признак восстановления не заменяет проверки владения manager lock.

## Проверки результата

- Смена manager после demotion старого мастера, до promotion нового, при RunCount=0: операция доходит до writable-мастера и завершения запроса, включая истёкший таймаут.
- Сбой сохранения признака или цели: соответствующие изменения MySQL не начинаются; повторная попытка повторяет запись.
- Перезапуск между записью признака и freeze: восстановление остаётся безопасным.
- Переключение без To: после начала перенаправления реплик смена manager сохраняет выбранную цель.
- Новый мастер уже записан в DCS: оформление результата завершается без повторного freeze; противоречие не превращается в ложный успех.
- Старый формат с StartedAt и RunCount=0 восстанавливается при известной цели; неоднозначная цель оставляет запрос с диагностикой.
- До начала изменений таймаут и лимит попыток продолжают работать; проверки кворума и сохранности данных сохраняются.

По уточнению объёма работ реализацию проверяем существующими тестами и минимальными юнит-проверками нового поведения; интеграционные сценарии в этой правке не расширяем. Прохождение этих проверок не является проверкой восстановления живого MySQL-кластера до writable-мастера.
